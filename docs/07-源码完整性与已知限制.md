# 07 · 源码完整性与已知限制

**动手前请先读这一章。** 这里说明哪些东西是可靠的、哪些是丢了或不确定的。

---

## 7.1 一句话结论

> **业务逻辑、常量、文案、数据模型：可靠度极高，可以照抄。**
> **Kotlin 语法形态、Compose UI 细节、构建配置：已丢失，必须重写。**

---

## 7.2 可靠性分级

| 内容 | 可靠度 | 依据 |
| --- | --- | --- |
| 包名、版本号、SDK 版本、权限、组件声明 | ★★★★★ | `AndroidManifest.xml` 解码结果，明文可读 |

| Kotlin 语法糖 | ☆☆☆☆☆ | 完全丢失 |

## 7.4 Kotlin → Java 丢失了什么

这是最本质的损失。编译器把 Kotlin 重塑成了 Java 能表达的形态，恢复不回去：

| Kotlin 特性 | 恢复后的样子 | 影响 |
| --- | --- | --- |
| `data class` | 手写的 `copy()` / `copy$default()` / `equals()` / `hashCode()` / `toString()` / `componentN()` | 噪音极大，但字段清单是准的 |
| `sealed class` | 普通抽象类 + 静态嵌套类 | 丢失穷尽性检查语义 |
| `suspend fun` | 带 `label` 字段的 `ContinuationImpl` + `switch(label)` 状态机 | **分支顺序需要人工恢复** |
| `@Composable fun` | `static void Foo(..., Composer $composer, int $changed)` | 完全不可读为 Compose 代码 |
| Compose lambda | `ComposableSingletons$XxxKt$lambda$123456$1` 之类的编译器生成类 | 类名里的数字是编译器哈希，无意义 |
| 内联函数 / `inline` | 代码被展开复制到调用处 | 出现大量「Code duplicated」 |
| 扩展函数 | 静态方法 `XxxKt.foo(receiver, ...)` | 能看懂，但不是原写法 |
| 默认参数 | 合成构造器 + `int mask` 位掩码 | **极易误读**（见下） |
| 具名参数 | 位置参数 | 可读性下降 |
| 空安全 `?` / `!!` | `Intrinsics.checkNotNull` 调用 | 可读 |
| 属性委托 | `getValue()` / `setValue()` 手工实现 | 可读 |
| 字符串模板 | `StringBuilder` 拼接 | 可读 |
| `object` 单例 | `INSTANCE` 静态字段 | 可读 |

### ⚠️ 位掩码陷阱（最容易读错的地方）

Kotlin 编译器为默认参数生成合成构造器，用 `int mask` 表示「哪些参数用了默认值」：

```java
// 恢复出的代码
new StylePreset("high_eq", "高情商", "🌤", Scene.GENERAL, "给足台阶，把话说圆",
    "你是高情商沟通教练。...", 0.0f, listOf(...), 64, null);
//                            ^^^^^ 这是假的！      ^^ 位掩码
```

`64` = 二进制 `1000000` = 第 6 位（temperature）被置位 = **该参数使用默认值**。
合成构造器里 `if ((mask & 64) != 0) temperature = 0.8f;` —— 所以运行时真正用的是 **0.8**，那个 `0.0f` 是 jadx 填充的占位值。

**本项目里 4 个风格（`high_eq`、`soft_no`、`subtle`、`opener`）都踩了这个坑。** `docs/04` 已经给出修正后的真实值。

同类陷阱还有：

- `NotificationCompat.CATEGORY_SERVICE` 实际就是字符串 `"service"` —— jadx 会把与已知常量相等的字符串替换成常量引用。本项目第 12 个风格的 id 就是这个情况。
- 颜色 `Color(4284169184L)` 是 `ARGB` 打包后的十进制，不是直观的十六进制。
- `copy$default` 的 mask 语义与构造器**相反**：mask 位置位表示「沿用原值」，清零表示「使用传入值」。

## 7.5 Compose UI：只能恢复「结构」，恢复不了「实现」

`ui/` 目录下的文件体积很说明问题：

| 文件 | 恢复后大小 |
| --- | --- |
| `components/ComponentsKt.java` | 165 KB |
| `ui/screens/HomeScreenKt.java` | 119 KB |
| `ui/screens/SettingsScreenKt.java` | 91 KB |
| `ui/screens/ResultScreenKt.java` | 78 KB |
| `ui/AppRootKt.java` | 75 KB |
| `ui/screens/HistoryScreenKt.java` | 70 KB |

里面混杂着大量 `Composer` 参数、`$changed` 位掩码、`ComposableSingletons$...$lambda$<hash>` 类、`remember`/`derivedStateOf` 的槽位管理代码。

**能读出来的**：
- 每个屏幕由哪些子组件构成、嵌套顺序
- 用了哪些 Material3 组件（`Text` / `Card` / `LazyColumn` / `Scaffold` / `OutlinedTextField` …）
- 组件的文案、颜色、尺寸参数
- `onClick` 之类的回调接到了哪个 ViewModel 方法

**读不出来的**：
- 原始的函数命名、参数命名、Modifier 链的书写顺序
- `@Preview` 组合
- 哪个状态用 `remember`、哪个用 `rememberSaveable`
- 动画参数、`Arrangement` / `Alignment` 的具体意图
- 组件拆分的粒度（编译器把很多小 Composable 内联了）

**建议**：UI 层不要试图「翻译」恢复结果，而是**照着重写**。文案和配色可以照抄（`docs/04`、`docs/05` §5.6 已整理），交互逻辑参考 `docs/05`。

## 7.6 完全丢失、无法恢复的东西

| 丢失项 | 说明 |
| --- | --- |
| `build.gradle` / `settings.gradle` 原文 | 已根据实测版本号**重建**（`android-project/`），但原文件里的注释、自定义 task、flavor 配置无从得知 |
| `gradle-wrapper.properties` | 只知道 Gradle 8.14.3 |
| ProGuard / R8 规则原文 | 已重建一份常规配置，但原规则（尤其 release 全量混淆的配置）丢失 |
| 签名密钥 | **不可恢复**。重新发布必须换新签名，无法覆盖安装原 App |
| 源码注释、KDoc | 全部丢失 |
| 原始文件名（部分） | 只能从 `compiled from: Xxx.kt` 注释知道文件名，如 `Models.kt`、`PromptBuilder.kt`；但一个 `.kt` 文件可能对应多个类，无法确定原始文件边界 |
| 单元测试 / 仪器测试 | APK 里不含 |
| Git 历史 | 无 |
| `assets/` 里的自定义资源 | debug 包的 `assets/` 是空的，release 包只有 `dexopt/baseline.prof` —— **原项目没有自定义 assets** |
| 自定义字体 | `res/` 里没有任何 `font/` 目录，主题用的是系统默认字体（`FontFamily` 传 `null`） |
| 自定义图片资源 | `res/drawable/` 只有 `ic_launcher_foreground.xml` 和 `ic_notification.xml` 两个自绘矢量图，其余都是 AndroidX 通知栏自带 |

## 7.7 无法交叉验证的部分

release 包被 R8 全量混淆（应用自身只剩 3 个类），因此：

- **无法用 release 包核对 debug 包的类名/方法名**是否与线上一致。
- 无法确认线上版本的**字符串常量是否被混淆**（R8 通常保留字符串字面量，所以文案大概率一致）。
- 无法确认 release 版是否**移除了某些代码分支**（如调试开关、`模拟会员状态`）。

## 7.8 需要人工确认的不确定点

以下内容在恢复时存在推断成分，重启前建议自己再判断一次：

| 项 | 现状 | 建议 |
| --- | --- | --- |
| `PersonaScreen` 的 UI 实现 | 未能完整恢复 | 按 `PersonaViewModel` 的 `save/delete` 反推 |
| 部分 `Code duplicated` 分支的**真实条件** | 15 个文件有重复控制流，jadx 会重复输出同一段代码 | 关键逻辑（配额、缓存、安全过滤）已逐一核对；UI 层可忽略 |
| `GenState.Failed` 的使用场景 | 生成路径上未观测到被设置 | 可能是为后续扩展预留；建议重写时要么用起来，要么删掉 |
| `MainUiState.canGenerate` 的完整条件 | 未逐位核对 | 大致是「输入非空 + 有选中风格 + 配额未耗尽」 |
| 断签提醒的触发精度 | WorkManager 周期任务，系统省电策略会影响 | 已实现，属预期行为 |
| 分享卡片的具体排版坐标 | `Canvas` 手绘，代码可读但数值密集 | 建议直接重设计，不必逐像素恢复 |

## 7.9 关于「重新发布」

⚠️ 两点必须提前知道：

1. **签名密钥无法从发布包中获取。** 包里只有公钥证书（`CN=Mouthpiece Test`，自签名测试证书），私钥不存在。重新发布的 APK 与原 App **签名不同**，老用户无法覆盖安装，只能卸载重装。
2. **原 App 未上线正式商店的迹象**：证书是 `Mouthpiece Test` 自签名测试证书，`AppInfo.CHANNEL = "内测版"`，`android:debuggable="true"`（debug 包）。说明 v0.1.4 是内测阶段产物，重新启动时可以放心重新设计包名/签名策略。
