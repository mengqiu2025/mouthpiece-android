# 06 · 重建与重启指南

## 6.1 先明确一件事

这份恢复产物里，**`source/` 是 Java，原项目是 Kotlin**。两者不是「格式不同」，而是**代码结构被编译器重塑过**。所以：

| 目标 | 可行性 |
| --- | --- |
| 读懂每一行业务逻辑 | ✅ 完全可行 |
| 复制常量、文案、提示词、风格目录 | ✅ 直接可用 |
| 把 `source/` 直接丢进 Android Studio 编译 | ❌ 不行，见 `docs/07` |
| 照着 `source/` 用 Kotlin 重写 | ✅ 这是推荐路径 |

`android-project/` 目录的 Gradle 结构、清单、资源都是**完整正确**的，可以直接打开；只有 Java 源码需要你按 Kotlin 重写。

## 6.3 推荐的落地顺序

按「依赖从少到多、逻辑从纯到杂」排：

### 第 1 步：`domain/`（约 10 个文件，零 Android 依赖）

先做这些，因为它们不依赖任何 Android API，可以直接写单元测试：

1. `Scene`、`ReplySource` —— 两个枚举
2. `AppSettings` —— 数据类 + 常量
3. `Persona`、`HistoryItem`、`Reply`、`ReplyRequest`、`QuotaState`、`ReplyKey` —— 纯数据类
4. `GenState` —— sealed class
5. `StylePreset` + `StyleCatalog` —— **风格目录可直接从 `docs/04` 抄**
6. `PromptBuilder` —— 提示词拼装（`docs/03` 有完整模板）
7. `SafetyFilter` —— 关键词过滤（`docs/05` §5.3）
8. `LocalTemplateEngine` —— 意图识别 + 模板轮换（`docs/04` §4.5）

### 第 2 步：`data/`（约 8 个文件）

1. `AiGateway` 接口 + `AiTimeouts` + `AiGatewayKt`
2. `OpenAiCompatGateway` —— 按 `docs/03` 实现（端点拼接、重试、错误翻译）
3. `SettingsStore` —— SharedPreferences，键名见 `docs/02` §2.2
4. `PersonaStore` —— SharedPreferences + `org.json`
5. `HistoryCodec` + `HistoryStore` —— 文件存储 + 备份 + 防抖
6. `ReplyRepository` —— 编排 + 缓存（缓存键算法见 `docs/02` §2.4）
7. `ShareCardRenderer` —— 如果暂时不做分享，可以先留空实现

### 第 3 步：`ServiceLocator` + `Application` + `MainActivity`

装配顺序、`sharedText` Channel 机制见 `docs/01` §1.4、§1.5。

### 第 4 步：`vm/`

`MainUiState` 是单一状态源，字段清单见 `docs/01` §1.3。`MainViewModel` 的公开方法签名可以直接从 `source/.../vm/MainViewModel.java` 抄（`onIncomingChange` / `toggleStyle` / `generate` / `regenerate` / `favoriteReply` / `shareReply` / `backToEdit` / `consumeMessage`）。

### 第 5 步：`ui/`

这部分工作量最大（原文件体积：`ComponentsKt` 165 KB、`HomeScreenKt` 119 KB、`SettingsScreenKt` 91 KB、`AppRootKt` 75 KB）。建议：

- 先照着 `source/.../ui/screens/*.java` 把每个屏的**结构**恢复出来（Compose 的 `@Composable` 在恢复出的代码里是可读的：能看到 `Text(...)`、`Column(...)`、`LazyColumn(...)` 的调用链和参数）。
- 文案直接复用 —— 全部中文文案都在 `source/` 里（`res/` 没有 strings.xml，所以文案只能从代码里找）。
- 主题配色见 `docs/05` §5.6 和 `source/.../ui/theme/ThemeKt.java`。

### 第 6 步：`push/`

WorkManager 部分完全独立，规则见 `docs/05` §5.7。

## 6.4 需要重新决策的几件事

恢复出来的项目有几个地方是「MVP 状态」，重启时值得先想清楚：

| 问题 | 原项目现状 | 建议 |
| --- | --- | --- |
| **模型调用方式** | 用户自带 Key，直连 OpenAI 兼容接口 | 若要做成商业产品，直连会让 Key 暴露在客户端，且无法计费。考虑改为自有服务端代理 |
| **会员/支付** | 只有本地 `is_pro` 开关，无支付 | 需要接支付 + 服务端权益校验 |
| **数据存储** | SharedPreferences + JSON 文件 | 数据量小时够用；若要做云同步/多端，建议换 Room + 服务端 |
| **安全过滤** | 24 + 8 条关键词硬编码 | 关键词表会持续过期，建议改为可远程更新的词库 + 模型侧审核 |
| **风格目录** | 硬编码 12 种 | 若要做成运营可配，建议改为服务端下发 |
| **网络层** | 裸 `HttpURLConnection` | 建议换 OkHttp + kotlinx.serialization，可读性和可维护性更好 |
| **DI** | 手写 `ServiceLocator` 静态单例 | 小项目够用；若继续长大建议上 Hilt |
| **Compose 版本** | 1.8.0（较旧） | 重建时可直接升到当前稳定版 |

## 6.5 从发布包重建「能跑的安装包」的备选路径

如果目标不是重写源码，而是**先让 App 能跑起来**，还有一条完全不同的路：

**apktool 解码 → 改 smali/资源 → 重新打包 → 签名**

工作区 `_reverse/tools/apktool.sh` 已经准备好了 apktool 3.0.3（依赖已解析到 `_reverse/tools/apktool-lib/`），可以直接：

```bash
cd "D:/AI Work Area/WorkBuddy/嘴替/_reverse"
bash tools/apktool.sh d -f -o apktool-debug apk/mouthpiece-0.1.4-debug.apk
# 修改后重新打包
bash tools/apktool.sh b apktool-debug -o rebuilt.apk
```

这条路能得到**可重建的完整工程**（smali + 解码后的资源），适合打补丁；但 smali 不是源码，不适合长期开发。
